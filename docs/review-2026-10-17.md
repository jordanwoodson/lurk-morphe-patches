# Code review — 2026-10-17

Reviewed `dev` at `aea51ab`, bundle version 1.11.1: 103 patches for Twitch 31.6.0,
Kick 40.32.1 and Rumble 3.21.0. The worktree was clean before this report. The scope
included each app's patches, injected Java/JavaScript, existing probes, documentation,
shared settings/player helpers and build/release automation.

The next cycle should focus on runtime correctness and repeatable verification before
adding more patches. Version pinning, unique fingerprint checks, settings registration,
and preservation of stock behavior when switches are off are useful foundations. The
main gaps are state transitions, asynchronous work and checks that are not run routinely.

**Findings to address**

1. **P2 — An expired sleep timer can pause newly started playback in Kick and Twitch.**
   Both helpers schedule a fallback three seconds after their initial pause, then inspect
   the current `SleepTimer.started()` set. Starting or resuming playback during those
   three seconds rearms the timer, but does not invalidate the old fallback. It pauses
   the newly started player anyway.

   Evidence: [KickPlayer.java, line 126](../extensions/shared/src/main/java/io/github/jordanwoodson/extension/shared/kick/KickPlayer.java#L126),
   [TwitchPlayer.java, line 108](../extensions/shared/src/main/java/io/github/jordanwoodson/extension/shared/twitch/TwitchPlayer.java#L108),
   and [SleepTimer.java, line 39](../extensions/shared/src/main/java/io/github/jordanwoodson/extension/shared/SleepTimer.java#L39).
   **Reproduced on the USB phone using freshly compiled production helpers:** playback
   started 100 ms after expiry was paused by the stale fallback in both implementations.
   Settings and player objects were test doubles; Android's Handler/Looper and the
   production timer/player helpers were real.

   Suggested fix: attach a generation to playback/timer expiry and ignore stale fallback
   work after a new start. Limit fallback candidates to the expiry-time players as well.
   A player snapshot alone will not protect a resumed instance. Retain regressions for
   both a new player and a resumed player, plus an actual player missed by the initial pause.

2. **P2 — Rumble's cookie-blocking switch needs restart semantics for its tracking effect.**
   If consent was allowed while the switch was off, enabling it blocks future Ketch
   entry calls but does not revoke the purposes already applied or stop SDKs already
   started in that process. The setting does not request a restart, while the effect
   table says it applies at the next resume.

   Evidence: [BlockCookieNoticePatch.kt, line 60](../patches/src/main/kotlin/io/github/jordanwoodson/patches/rumble/consent/BlockCookieNoticePatch.kt#L60)
   and [rumble.md, line 153](rumble.md#L153). Existing stock 3.21.0 smali confirms the
   cached-consent application occurs during startup and tracker dispatch has a one-time
   latch; the resume path loads Ketch without resetting the granted purposes.
   This is a code-level finding, not a new live traffic measurement. The separate
   Disable analytics patch can independently suppress some traffic.

   Suggested fix: set `restart = true` and explain that the full tracking effect takes
   effect after restarting. Verify off → consent granted → on → restart, including
   the documented push-notification consequence.

3. **P2 — Twitch ad-replacement HTTP work does not enforce its total time budget.**
   `http()` computes the remaining timeout once, assigns it independently to connect
   and read operations, and then reads the complete body without checking the deadline.
   A response that trickles data can outlive the six-second budget. These requests run
   while replacement logic holds the stream lock, so slow requests can stall other
   playlist work too.

   Evidence: [TwitchBackupStream.java, line 894](../extensions/shared/src/main/java/io/github/jordanwoodson/extension/shared/twitch/TwitchBackupStream.java#L894),
   its `readAll()` at line 926, and the stream lock at line 371. Static finding; no
   slow-network reproduction was run in this review.

   Suggested fix: enforce one monotonic deadline across connection, headers and body,
   with cancellation and a response-size limit. Extend `AdBackupProbe` with slow-header,
   trickling-body and cancelled-request fixtures. Check that failure promptly returns
   to the existing playback fallback.

4. **P2 — Rumble misses mention identity when joining a chat with no history.**
   `messages()` returns immediately for an empty message list, before `userNames()` can
   learn the signed-in user's name from the DTO's users. Mention highlighting cannot
   recognize that user until a later DTO supplies their entry. Identity discovery is
   also conditional on Chat keywords being enabled, leaving a similar late-enable gap.

   Evidence: [RumbleChat.java, line 94](../extensions/shared/src/main/java/io/github/jordanwoodson/extension/shared/rumble/RumbleChat.java#L94)
   and username assignment at line 164. **Reproduced on the USB phone using the current
   production helper:** an empty history learned no name; the same users with one
   history message correctly learned `lurker`. This verifies helper behavior rather
   than a signed-in server event.

   Suggested fix: discover identity independently of message count and filtering state.
   Extend [KeywordsProbe.java](../tests/rumble/KeywordsProbe.java) with empty history,
   enable-after-join and account-change cases; retain its existing signed-out control.

5. **P2 — Stable release recovery omits the merge back into `dev`.**
   Normal stable publication calls `backmerge()`. If publication fails after the
   release commit/tag is pushed, a later run publishes through `finish_unpublished()`,
   which returns without that merge. With no new release-worthy commits, the normal
   release path does nothing and `dev` remains without the recovered stable commit.

   Evidence: [release.py, line 321](../.github/scripts/release.py#L321), compared with
   the normal path at line 405. **Reproduced through `main()` with external operations
   mocked:** the recovery published successfully and never called `backmerge()`.

   Suggested fix: make stable-release finalization idempotent and shared by normal and
   recovery paths. Preserve/restore the intended branch when finalization switches
   branches. Test publication failure, recovery with no new commits, an advanced `dev`,
   and recovery after a merge-back failure.

6. **P2 — An existing Twitch helper test no longer compiles, and CI never catches it.**
   `tests/twitch/verify_interface.py` fails because its `Settings` double lacks
   `getInt(String)` and its `Bundle` double lacks `get(String)`, both now called by
   production `TwitchInterface`. The failure occurs before its behavioral assertions.

   Evidence: [verify_interface.py, line 17](../tests/twitch/verify_interface.py#L17).
   **Reproduced with the installed JDK 21.** Both CI workflows build the patch bundle
   but run none of the helper checks. The claim that all tests need an APK or device
   is too broad: four standalone production-helper checks passed in this review.

   Suggested fix: repair the boundary doubles and add coverage for the newer startup-tab
   and Home-tab behavior. Add one host-test command and invoke it in PR CI and before
   publishing releases. Keep APK/Hermes and device checks as separately selectable
   stages with explicit prerequisites.

7. **P3 — Twitch VOD chapter requests need concurrency and cache bounds.**
   Prefetch starts a thread whenever a result is not yet cached; tapping Chapters starts
   another independent request. There is no request-in-progress map, failure backoff or
   eviction from the successful-result cache.

   Evidence: [TwitchVod.java, line 334](../extensions/shared/src/main/java/io/github/jordanwoodson/extension/shared/twitch/TwitchVod.java#L334),
   the dialog request at line 278 and cache at line 84. Static finding; thread or memory
   exhaustion was not observed.

   Suggested fix: share in-flight requests through a bounded executor, cap the cache,
   and briefly cache failures. Verify repeated loads/taps issue one request, and that
   leaving a video does not present an obsolete chapter dialog.

8. **P3 — A stalled Kick emote lookup can hold back successful global emotes.**
   The chat script has no fetch deadline and waits for channel and global requests
   together before rendering either result.

   Evidence: [chat-page.js, line 65](../patches/src/main/resources/kick/chat/chat-page.js#L65).
   Static resilience finding; no live provider outage was simulated.

   Suggested fix: add abort deadlines and allow global emotes to appear when channel
   lookup fails or stalls, preserving channel-name precedence when it succeeds. Add
   stalled-owner and stalled-provider cases to the browser test.
